## 3. 设计决策

1. **SSE 路由按线级协议验证**：通过 `TestClient` 请求真实 `/chat/stream` 路由，只 monkeypatch service generator，解析 `event:`/`data:`，验证顺序、JSON 格式、结构化 done、异常转换和提前结束。
2. **SQLite 完全隔离**：repository/API 测试把 `app.db.database.DATABASE_PATH` monkeypatch 到 pytest `tmp_path`，不写项目根 `tutor_agent.db`。
3. **备份完全隔离**：所有源目录、输出目录和归档解压目录均位于 `tmp_path`；SQLite 使用真实 `sqlite3 backup` 路径验证可读性与 `integrity_check`。
4. **前端分层测试**：API 层使用 mock ReadableStream reader 验证请求与 SSE 分派；App 层 mock `postChatStream` 验证文本累积、done/error 后发送状态清理及关闭流式时回退普通 chat。
5. **范围外生产缺口用严格 xfail 固化**：要求生产修改但文件不在允许范围内的缺口使用 `pytest.mark.xfail(strict=True)`，既记录预期失败，又能在将来实现修复后以 XPASS 使测试失败，提示移除 xfail。

## 6. TDD/失败尝试记录

1. 首次收集 journal API 测试失败：PowerShell 字符串替换把字面量 `\n` 写入 import，导致 `SyntaxError`；修复测试文件写入方式后重跑。

3. 前端 API 首次新增测试因同类字面 CRLF 写入导致 Vite parse error；改用逐行写入后重跑。
4. App SSE 状态测试最初使用“发送按钮恢复 enabled”断言；发送后输入框为空会使按钮因 `canSend` 仍 disabled，改为检查流式开关恢复 enabled，只观察 `isSending`。
5. 后端全量测试发现 3 个本工作包外契约失败：旧测试未接受新增的 `save_journal_entry` 工具和 `journal` persona；对应测试文件不在允许范围，未修改。

## 8. 已知风险与未解决问题

1. **备份不完整**：`scripts/backup.py` 当前仅收集 SQLite 与 Chroma，未打包 corpus 和附件目录。
2. **缺源仍成功**：SQLite 与 Chroma 均不存在时仍生成空归档；虽有 warning，但没有失败异常/非零返回分类。
3. **标签误匹配**：journal 标签使用 substring `LIKE`，`api` 会匹配 `fastapi`。
4. **输入校验不足**：journal API 接受非法 `entry_date` 与空 `content`。
5. **前端流式 error 语义有限**：API SSE `error` 事件只触发 callback，不 reject；App 会清理发送态但仍用空 fallback reply 完成消息。本工作包按现有契约测试，没有改生产行为。
6. **后端全量非绿**：3 个旧测试需由对应工作包更新工具/persona 期望。
