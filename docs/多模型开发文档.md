文档一：需求文档
v1.1 多模型选择 状态：待评审 ｜ 依赖：v1.0 ReAct + RAG + MCP ｜ 归档路径建议：docs/v1.1-multi-model.md

1. 背景
   当前系统只能接一个模型。app/config.py 的 load_llm_config() 读取 OPENAI_API_KEY / OPENAI_BASE_URL / OPENAI_MODEL 三个环境变量，TutorAgentService 在进程启动时把 client 固化为单例，ReactOrchestrator 里 4 处硬编码 model=self.config.model。

.env.example 已预留 DEEPSEEK_* 三个变量，但 config.py 从未读取。

2. 目标
   用户可在每条消息上自由选择模型，同一会话可混用
   新增模型只需改 .env + 一处 catalog 常量，不改业务逻辑
   支持 DeepSeek V4 的 thinking 模式并向用户展示思考过程
   修复流式路径的重复模型调用，使成本与延迟数据可信
3. 范围
   做： 模型 catalog 与 /models 接口 · 按消息选模型 · 客户端连接池 · 输出格式从五字段 JSON 改为 Markdown · thinking 流式展示 · 单次流式调用改造 · 历史数据版本化 · 按模型的 token/延迟统计

不做： 用户自带 key（BYOK）· 模型管理后台 · 自动 fallback 切换 · 按模型计费与配额 · 更换 Embedding/Rerank 模型 · Responses / Anthropic wire protocol（仅预留字段）

4. 名词
   术语    定义
   model_id    前端可见的选项标识，如 ds-pro-deep。一个 model_id = 一个模型名 + 一组固定参数
   api_model   实际发给厂商的 model 值，如 deepseek-v4-pro
   ModelSpec   一个 model_id 的完整能力与参数声明，定义在代码中
   Provider    一组 base_url + api_key，多个 model_id 可共享
   Agent-generated table
   注意 model_id 与 api_model 是多对一。 DeepSeek V4 靠 thinking 请求参数切换思考模式，同一个 deepseek-v4-pro 可衍生出多个用户可选项。

5. 功能需求
   FR-1 模型目录
   FR-1.1 MODEL_CATALOG 定义在 app/services/agent/model_registry.py，包含 model_id / display_name / provider / api_model / supports_tools / supports_thinking / wire_api / top_level_params / extra_body / concurrency_hint。OpenAI SDK 已声明的参数放 top_level_params，厂商扩展请求体放 extra_body
   FR-1.2 .env 的 ENABLED_MODELS（逗号分隔 model_id）控制启用范围
   FR-1.3 启动时求交集：在 catalog 中 ∩ 在 ENABLED_MODELS 中 ∩ provider 的 key 已配置。任一不满足则该模型不可用
   FR-1.4 交集为空时启动即失败并打印缺失原因，不允许静默启动一个没有模型的服务
   FR-1.5 DEFAULT_MODEL_ID 指定默认模型，必须在可用集合内
   FR-2 模型列表接口
   FR-2.1 GET /models 返回可用模型数组：model_id / display_name / description / supports_thinking / is_default
   FR-2.2 不得返回 api_key、base_url、api_model
   FR-2.3 响应形态对齐现有 GET /personas
   FR-3 按消息选择
   FR-3.1 ChatRequest 新增 model_id: str | None，为空时用 DEFAULT_MODEL_ID
   FR-3.2 不在可用集合内时返回 422，body 为 {"error": "invalid_model_id", "model_id": ..., "available_models": [...]}，对齐现有 invalid_persona_id
   FR-3.3 同一会话允许逐条切换模型，不做类似 SessionPersonaMismatchError 的一致性校验
   FR-3.4 切换模型后，新模型可见此前全部历史（共享上下文），不因换模型截断
   FR-3.5 ChatResponse 回传实际使用的 model_id
   FR-4 客户端管理
   FR-4.1 OpenAI client 按 provider 缓存复用（同 provider 的多个 model_id 共用一个 client）
   FR-4.2 缓存必须线程安全。chat_stream 是同步 def，FastAPI 在线程池中执行，存在并发写入
   FR-4.3 TutorAgentService 不再持有 self.client，改为按请求解析
   FR-5 输出格式改造
   FR-5.1 移除 STRUCTURED_REPLY_PROMPT 的五字段 JSON 强制约束
   FR-5.2 改为 prompt 软引导：建议模型用 ## 下一步 ## 小练习 等 Markdown 小标题收尾，后端不做机器解析，模型未遵守也不得报错或降级
   FR-5.3 TutorReply 塌缩为 answer: str + sources: list[Source]，移除 next_task / exercise / checkpoints / source_ids
   FR-5.4 移除 response_parser.py 中返回硬编码假回复的兜底分支
   FR-5.5 引用来源改为用 _CITATION_PATTERN（tutor_agent_service.py 第 41 行）从正文提取，再经 ledger 白名单校验。安全强度不变，仅去掉模型自报环节
   FR-6 Thinking 展示
   FR-6.1 流式响应新增 SSE 事件类型 thinking
   FR-6.2 前端在气泡上方以默认折叠的区块展示，标题含耗时
   FR-6.3 思考内容不落 SQLite、不进入后续用户轮次；同一次请求的 ReAct 工具循环内必须回传 reasoning_content
   FR-6.4 思考 token 必须单独统计（见 FR-8.2）
   FR-6.5 supports_thinking=False 的模型不发此事件，前端不渲染折叠区
   FR-7 单次流式调用
   FR-7.1 run_stream 的每轮只调用一次模型，流式发起，tools= 与 stream=True 同时传入
   FR-7.2 从 stream 增量中分别累积 content / reasoning_content / tool_calls；tool_calls 按 index 分组，arguments 字符串分片拼接后再 json.loads；产生工具调用时，累积后的 reasoning_content 必须写回 assistant 消息，再与工具结果一起发送给模型
   FR-7.3 删除 _stream_final_reply 的二次调用路径
   FR-7.4 Preamble 处理：若某轮先产出正文再产出 tool_calls，已推送的正文视为合法可见内容予以保留（形如"我先查一下你的笔记…"），不回滚 UI。落库的 answer 为各轮可见正文的顺序拼接
   FR-7.5 流式失败时回退非流式，回退路径必须同样带 tools=（现有回退丢了工具，是隐性缺陷）
   FR-8 可观测性
   FR-8.1 单次流式调用必须完成 timings.bump("llm_calls") / timings.track("llm") / _record_llm_call() 三项埋点。当前 _stream_final_reply 三项全无
   FR-8.2 llm_calls 表新增 reasoning_tokens INT
   FR-8.3 agent_traces.model / llm_calls.model 写入 model_id（非 api_model），便于区分同一模型的不同参数组
   FR-8.4 流式请求传 stream_options={"include_usage": True} 获取 usage。若 provider 不支持，需记录为空而非估算填充
   FR-9 历史数据版本化
   FR-9.1 conversations 表新增 reply_format TEXT NOT NULL DEFAULT 'json_v1'
   FR-9.2 存量数据由 DEFAULT 自动标记，不迁移、不清空
   FR-9.3 新写入标记 markdown_v2
   FR-9.4 读取时按 format 字段分发 parser，严禁用"试 JSON 解析失败则当纯文本"的嗅探式判断 —— 本项目回答常含 JSON 代码块，嗅探必然误判
   FR-9.5 列迁移复用 database.py 第 409 行 _ensure_conversations_session_id_column() 的既有模式
   FR-10 前端
   FR-10.1 新增 ModelSelector.jsx，形态对齐 PersonaSelector.jsx
   FR-10.2 选择结果存 localStorage，刷新后保持
   FR-10.3 localStorage 中的 model_id 已不在 /models 返回值中时，静默回落默认模型
   FR-10.4 ChatMessage.jsx 移除五字段分区渲染，仅保留 MarkdownAnswer
   FR-10.5 每条 AI 消息标注所用模型
   FR-10.6 流式渲染 thinking 折叠区与正文两个通道
6. 非功能需求
   项  要求
   延迟    首字延迟应显著下降（消除一次完整非流式调用）。改造前后各采样 20 次记录 P95
   成本    无工具轮次的 token 消耗应约降至原先一半
   兼容    不改 Embedding / Rerank 配置。换 chat 模型不得影响向量检索
   安全    key 仅存 .env，不出现在任何 API 响应、日志、trace 中
   并发    Flash 上限 2500、Pro 上限 500，差 5 倍。concurrency_hint 本期只存不用
   可回滚  ENABLED_MODELS 只留一个模型即可回到单模型行为
   Agent-generated table
7. 验收标准
   GET /models 返回 ≥2 个模型，响应中不含任何密钥或 base_url
   同一会话连续两条消息用不同模型，第二个模型能正确引用第一条的内容
   传入不存在的 model_id 返回 422 且列出可用模型
   一次无工具调用的对话，llm_calls 表只有一条记录（改造前为一条，但实际发生两次调用）
   thinking 模型的响应中 reasoning_tokens > 0 且已入库
   前端能看到折叠的思考过程，展开有内容
   改造前存入的历史对话仍能正常显示，reply_format 为 json_v1
   模型回复不含任何 JSON 时，正常渲染为 Markdown，不出现"你知道 fallback 是用来兜底异常输出的"
   .env 中 ENABLED_MODELS 移除某模型后重启，该模型从前端下拉框消失
   后端 pytest 全绿，前端 npm run build 与 npm run lint 通过
8. 风险
   风险    等级    应对
   流式 tool_calls 分片累积实现错误，导致工具调用失效  高  先写单测覆盖分片拼接，用录制的 chunk 序列做 fixture，再接主流程
   去掉 JSON 后教学结构退化，Agent 变普通聊天机器人    中  prompt 软引导 + 人工验收 10 轮对话质量
   stream_options.include_usage 部分 provider 不支持   中  usage 缺失时留空，不估算。FR-8.4
   Preamble 正文与工具结果混排导致回答语义割裂 中  先观察真实表现，必要时在 prompt 中约束"调工具前不要长篇输出"
   前端 localStorage 存了失效 model_id 低  FR-10.3 静默回落
   reasoning_content 未随 assistant 工具调用消息回传导致请求返回 400 高  Step 3 同时完成 reasoning 累积、回写与 thinking + 工具调用 + 多轮测试；这是协议硬要求，不按偶发错误处理
   Agent-generated table
