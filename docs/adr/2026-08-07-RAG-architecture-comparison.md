# ADR: RAG 架构方案对比（统一单集合 vs 多集合 + 模型路由）

> 状态：Proposed（待对比评测后决策）
> 日期：2026-08-07
> 评测集：`tests/data/`（扩展中）

## 背景

Tutor Agent 当前的 RAG 系统存在割裂问题：

- `learning_notes` 集合（8333 块）：学习笔记 + 项目文档 + self-llm 语料
- `job_descriptions` 集合（970 条）：公共 JD（父子结构，检索子 → 返回完整父）
- 两个集合由不同工具调用，`search_job_descriptions` 已移植但未注册

用户希望重构为统一的 RAG 知识系统，覆盖**学习笔记 + 项目文档 + 面试 JD** 三类数据。

在架构选型上存在两种方案，各有优劣，本 ADR 记录两种方案的设计与对比评测方法，用数据决策。

> **工具注册策略**：此前曾计划“只注册 web_search”以排除工具干扰，该计划已收回。
> 本次对比评测需要引入检索工具（`search_learning_notes`、`search_job_descriptions`），
> 因此恢复相关工具注册，评测完成后再根据结果收敛。

## 方案 A：统一单集合（合成）

### 设计

把学习笔记、项目文档、JD 全部切块后存入**同一个 Chroma 集合**（如 `knowledge`），通过 metadata 区分类型：

```text
knowledge 集合
  ├─ doc_type=note     → 学习笔记块（source=docs/...）
  ├─ doc_type=project  → 项目文档块（source=corpus/self-llm/...）
  └─ doc_type=jd       → JD 子向量（parent_id, child_type=jd_text/job_info）
```

- 建索引：一个脚本统一切块、embedding、写入
- 查询：query 向量化 → 一次 ANN 检索 → 覆盖所有类型
- JD 命中子向量 → 通过 `parent_id` 找回完整父文档

### 优点

- **无路由**：一次 ANN 天然覆盖所有类型，不依赖模型判断
- **相似度可比**：所有数据同一向量空间，同一距离度量
- **实现简单**：一套检索逻辑，一套索引

### 缺点

- 搜索空间大（8333+970 块），理论上召回噪音略多
- metadata 要统一设计，兼顾笔记普通块和 JD 父子结构

## 方案 B：多集合 + 模型路由（ReAct 自选）

### 设计

保持多个集合（`learning_notes`、`job_descriptions`），**不做独立路由器**，而是让模型在 ReAct 循环中**自己选择调用哪个检索工具**：

```text
用户提问
  → 模型在 ReAct 循环中分析
  → 模型自己决定：调用 search_learning_notes（查笔记）？还是 search_job_descriptions（查 JD）？
  → 只查对应集合（搜索空间小）
```

### 优点

- **搜索空间小**：模型选对时，检索更精确
- **保留各集合独立 schema**：JD 的父子结构、过滤字段天然独立

### 缺点

- **依赖模型判断**：模型选错索引 → 检索失败
- **模型可能不调**：`tool_choice="auto"` 时模型可能直接回答不检索
- 工具越多，ReAct 越容易乱（这是重构的原始动机之一）

## 对比评测方法

### 指标

| 指标 | 含义 | 计算 |
|------|------|------|
| **Recall@k** | 召回率 | 检索到的相关文档数 / 应有相关文档数 |
| **Precision@k** | 精确率 | 检索到的相关文档数 / 检索返回总数 |
| **端到端回答质量** | 生成质量 | 人工/LLM 审核（faithfulness、completeness） |

### 评测集设计

需要覆盖三类数据的问题：

1. **学习笔记类**（现有 `retrieval_eval.jsonl` 35 条 + `joint_retrieval_eval.jsonl` 84 条可复用）
2. **项目文档类**（现有评测集已部分覆盖）
3. **面试 JD 类**（**需新增** 20-30 条）

JD 类评测用例覆盖范围：

| 类型 | 示例 | 期望来源 |
|------|------|---------|
| 岗位职责类 | "RAG 后端岗位主要做什么？" | `corpus/JD/...` |
| 技能要求类 | "Agent 开发岗要求哪些技能？" | `corpus/JD/...` |
| 薪资/学历类 | "大模型岗位的薪资范围？" | `corpus/JD/...` |
| 跨类混合 | "想做 RAG 相关工作，该看什么岗位和笔记？" | JD + 学习笔记 |

### 评测流程

```
同一份评测集
  → 方案 A 跑一遍（统一检索）
  → 方案 B 跑一遍（模型路由）
  → 对比 Recall / Precision / 回答质量
  → 用户审核最终质量
```

### 端到端质量审核

评测不仅产出指标报告，还要**详细审核过程**：

- 每个用例的完整调用链（模型选择了什么工具、检索了什么、基于什么回答）
- 引用是否真实、来源是否匹配
- 检索错误路径（模型选错索引、未检索直接答）单独记录
- 审核结果由用户最终确认

### 实现方式：同一系统 + 配置开关

两种方案在**同一份代码**中实现，通过配置开关切换：

```text
RAG_MODE = "unified"   # 方案 A：统一单集合
RAG_MODE = "routed"    # 方案 B：多集合 + 模型路由
```

**优点**：
- 同一份评测脚本直接 A/B，不用跨分支
- 开关切换成本低，便于反复对比
- 决策后删除另一分支逻辑即可

## 决策标准

| 维度 | 权重 | 说明 |
|------|------|------|
| Recall@k | 高 | 检索不到 = 回答必然失败 |
| Precision@k | 中 | 检索噪音多 = 回答质量下降 |
| 端到端回答质量 | 高 | 用户最终感知 |
| 实现复杂度 | 低 | 谁简单谁优先 |
| 可维护性 | 中 | 后续加数据源、分片是否方便 |

> 最终决策由用户审核评测结果后确定，不预设结论。

## 影响与后续

- 决策后，被选方案成为主链路，另一方案代码移除
- 统一 metadata schema 设计（方案 A）或保留独立 schema（方案 B）
- JD 父子结构在两种方案下如何保留（方案 A：metadata `parent_id`；方案 B：天然保留）
- 后续可评估分片（subject sharding）作为扩展
